# BitCraft Companion on Vercel: design

Date: 2026-11-24 · Status: **approved on 2026-11-24**, in the original repository, no fork. The open questions follow the recommended defaults (see "Open decisions").

## Intent

Move BitCraft Companion to Vercel, **for free**, without depending on a PC that stays on. The change is made **in the repository itself** (`vdarakjian/bitcraft-companion`), with no fork. The app does the same as today: look up recipes and items, calculate costs (calculator and plans with steps, buildings and gathering) and track the group's inventory through the public BitJita API. It remains an app for two people.

The current app (AdonisJS 7, SQLite, Edge, htmx and Alpine) does not fit on Vercel:

- Vercel does not keep files between executions, and SQLite would be lost;
- there is no continuous process for the 15-minute sync timer;
- AdonisJS has no official support there.

So the app is **rewritten in Next.js**, porting the logic that already exists and is tested (calculator, importer, sync), rather than reinventing it.

The old AdonisJS design docs (`2026-11-21-*`) live only in git history.

## Decisions already made

- **Stack:** Next.js (App Router, TypeScript), Prisma, Postgres on Neon and Chakra UI. Interface in pt-BR, code in English and item names as they come from the game.
- **On-demand inventory sync:** when someone opens a page that uses the inventory and the last sync is more than 15 minutes old, the app syncs. There is also a daily Vercel Cron. Never a 15-minute timer.
- **Game data import:** a script run from André's PC against the Neon database, not a Vercel function. It keeps handling what is new, what was removed (`removed_at`) and what was renamed.
- **Login on:** the app is public at `*.vercel.app`. Two accounts, created by script, no open signup.
- **Game rules, no exceptions:**
  - only the public BitJita API;
  - never connect to the game servers (SpacetimeDB) with a player token;
  - never store a token;
  - no reducers or automation.

## Limits that drive the design

| Service (free plan) | Limit | Consequence for the design |
|---|---|---|
| Vercel Hobby | No persistent disk | All data lives in Postgres. |
| Vercel Hobby | Cron at most once a day, at an approximate time | On-demand sync, plus a daily cron. |
| Vercel Hobby | Function of at most 300 s | The sync of two characters takes a few seconds (5 to 6 calls to BitJita, spaced 500 ms apart). The import does not run on Vercel. |
| Vercel Hobby | Personal use, not commercial | That is the case here. |
| Neon Free | 100 CU-hours of compute per month, per project | The database sleeps after 5 idle minutes, and nothing may wake it every 15 minutes. Fix the compute at 0.25 CU: 100 CU-hours give 400 hours awake per month. |
| Neon Free | 1 GB of storage | The current database is 5.5 MB. In Postgres, with indexes, it should be between 20 and 30 MB. |
| Neon Free | 5 GB of transfer per month | Loading the calculator's recipe graph by reading the tables costs about 2.5 MB at every cold start. That is why the graph is stored compressed (see "Recipe graph"). |
| Neon Free | When a limit is exceeded, the compute is suspended until the next cycle | If that happens, the app is down until the next cycle. Watch the usage in the Neon console during the first month. |

The Neon numbers were checked on 2026-11-24, in the [limits FAQ](https://neon.com/faqs/free-plan-limits-and-quotas) and in the [October 2026 changelog](https://neon.com/docs/changelog/2026-10-02), which raised the storage to 1 GB.

## Structure and conventions

The app follows the same Rails conventions the project already uses, translated to Next.

| Rails | Adonis (today) | Next |
|---|---|---|
| RESTful `resources` | `router.resource()` | Folders in `src/app/` with the same URLs as today (`/plans`, `/plans/[id]`, `/recipes`, `/items/[id]`, `/inventory`, `/game_players`). Mutations in server actions, one `actions.ts` per resource (`createPlan`, `updatePlan`, `destroyPlan`…). |
| Thin controllers | Controllers | Pages (server components) and actions only read the input, validate, call a service and render or redirect. Rules live in `src/services/` and `src/models/`. |
| Service objects | `app/services/<area>/<name>.ts` | `src/services/<area>/<name>.ts`, ported almost unchanged. |
| Models | Lucid with scopes | Prisma has no classes. The queries and rules of each table live in `src/models/<model>.ts` (for example `recipe.ts` with `searchRecipes` and `filterOptions`, and `plan.ts` with `toCalculatorState` and `savePlanState`). The "`active` scope" becomes an `active = { removedAt: null }` filter, exported and used in every game data query. |
| Strong params | VineJS in `app/validators/` | Zod in `src/validators/<resource>.ts`, one schema per resource and action. |
| Migrations | Lucid | `prisma migrate`. Never edit an applied migration. SQL that Prisma cannot express (partial index) goes in the migration itself. |
| `db/seeds.rb` | Seeders | `prisma/seed.ts`, for dev and test only. The game data comes from the import script. |
| Rake tasks | `ace` commands | Scripts in `scripts/`, run with `tsx` through `npm run` (see the table below). |
| Partials and layouts | Edge components and htmx responses | App Router layouts and React components with Chakra in `src/components/<area>/`. Client components only where there is interaction. |
| Specs | Japa | Vitest: `tests/unit/` without a database and `tests/integration/` with Postgres, plus the fixtures in `tests/fixtures/`. |

The commands look like this:

| Today | In Next |
|---|---|
| `node ace bitcraft:import [--commit=sha] [--path=pasta]` | `npm run game-data:import -- [--commit=sha] [--path=pasta]` |
| `node ace users:create --email= --name=` | `npm run users:create -- --email= --name=` (the password is prompted for, hidden) |
| `node ace inventory:sync` | `npm run inventory:sync` |
| `node ace migration:run` | `npx prisma migrate dev` (local) and `npx prisma migrate deploy` (Neon, run from the PC) |
| `npm run dev` (port 3333) | `npm run dev` on port **3100** (3333 and 3000 are taken by the current app) |

## Prisma schema

The schema comes from the 18 applied Lucid migrations, already in its final state: without the `game_credentials` table, which was created and then dropped, with the `source` column in `extraction_recipes` and with `plans.use_inventory`.

Changes relative to SQLite, each with its reason:

1. **Game IDs are `Int`, not `BigInt`.** The largest ID in the current data is 2,147,483,647, exactly the maximum of Postgres `integer`. `BigInt` would become `bigint` in JavaScript and complicate JSON and comparisons. If a patch brings a larger ID, the import fails with a database error, not silently, and then a migration to `BigInt` is created.
2. **`items.item_list_id` is new:** an FK to `item_lists.id`, resolved by the importer after saving the lists. Today the link is made through `item_list_game_id`, with no FK. With the FK, Prisma can navigate from item to list in queries (`include`), and the recipe search by random-output content becomes an ordinary relation. `item_list_game_id` is still stored, as it comes from the game.
3. **`item_list_possibilities.position` is new,** unique together with `item_list_id`. Today the importer inserts each possibility in a separate call to learn the ID: about 6 thousand round trips to the database, which is slow over the network to Neon. With the position, all of them go in a single `INSERT`, and the IDs are read back by the key (`item_list_id`, `position`).
4. **`last_import_id` becomes a plain column, without an FK.** A Prisma relation requires the inverse side in `GameDataImport` for every table, and imports are never deleted.
5. **Postgres enums** for the closed sets: item kind, recipe kind, gathering source, inventory location, entry source, and the sync trigger and status.
6. **`sync_runs.trigger`** goes from `manual | schedule` to `manual | auto | cron`:
   - `manual` is the button;
   - `auto` is the sync because the data is stale when a page is opened;
   - `cron` is the daily one.
7. **New tables:**
   - `recipe_graph_snapshots`, the compressed calculator graph, written by the import;
   - `login_attempts`, to limit login attempts.
8. **Partial index** `sync_runs (status) WHERE status = 'running'`, unique, created with SQL in the migration. It is the "one sync at a time" lock across Vercel instances, replacing today's in-memory lock.
9. **Dates in `timestamptz`.** They are displayed in the `America/Sao_Paulo` time zone, because Vercel functions run in UTC.

Two Postgres differences that the ported logic must take into account:

- **SQLite's `LIKE` ignores case; Postgres's does not.** Searches become `ILIKE` (in Prisma, `mode: 'insensitive'`), with the same escaping of `%` and `_`.
- **Ordering by name follows the database collation,** not SQLite's binary order. Tests that check ordering use names that do not depend on this.

With 9.3 thousand items and 8.8 thousand recipes, an `ILIKE` without an index answers in a few milliseconds. A trigram index (`pg_trgm`) only comes in if the search gets slow.

## Calculator recipe graph

Today the `RecipeGraph` loads all active recipes into memory (about 9 thousand recipes and 20 thousand ingredients) and caches them until the next import. On Vercel, every new instance would have to redo that loading: six queries and about 2.5 MB coming from Neon at every cold start.

**On Vercel:**

- **The import builds the graph** with the same logic as today, split into two functions:
  - `loadGraphRows(db)`, which runs the queries;
  - `buildRecipeGraph(rows)`, pure, which builds the graph.
- **The import also stores the graph** in `recipe_graph_snapshots`, as compact JSON (arrays, not objects) compressed with gzip. The estimate is 400 to 600 KB. This happens in the same transaction as the import.
- **In the app, `getRecipeGraph()`:**
  1. reads the id of the last finished import (a small query, which the layout already makes to show "Dados do jogo de …");
  2. if it is the id of the instance's cache, uses the cache;
  3. if not, reads the snapshot, decompresses it and builds the `Map`s.
- **Without a snapshot** (for example, after an import made before this change), the app builds the graph from the queries and warns in the log.

This way, each cold start costs one query of about 0.5 MB instead of six queries with 2.5 MB. With 5 GB of transfer, that is enough for about 10 thousand cold starts per month. Vercel's fluid compute reuses instances, so two users should generate a few dozen per day.

The planner (`production_planner.ts`) and the presenter remain pure functions and are ported as they are. The planner runs on the server, in the calculator and plan pages, as today.

## Inventory synchronization

What is ported with no change of rules:

- `bitjita_client.ts`:
  - `User-Agent: bitcraft-companion`;
  - 15 s timeout;
  - at most 2 calls per second;
  - the `NotFoundError`, `RateLimitedError` and `UpstreamError` errors.
- `inventory_source.ts`: the `InventorySource` interface, the BitJita source and the inventory classification, already validated with real responses.
- `inventory_sync.ts`:
  - saves per player, each in its own transaction;
  - a failure keeps that player's previous data;
  - a 429 stops the following calls;
  - unknown items are counted, and the warning suggests running `npm run game-data:import`;
  - the claim chests stay off, with `readClaims` to turn them back on.

What changes because of Vercel:

1. **The lock comes from the database.** The in-memory lock (`static #running`) does not hold across instances, so it goes away. The sync inserts a `sync_runs` row with status `running`. If the unique partial index refuses it, another run is already in progress, and the response is "Já existe uma sincronização em andamento." Before inserting, a `running` run older than 5 minutes is closed as `failed` ("Interrompida antes de terminar"). Today that limit is 10 minutes; on Vercel, the function dies at 60 s.
2. **On demand (`trigger = auto`):**
   - The pages that show the inventory are `/inventory`, `/plans/[id]` and `/calculator` (the last two when "Usar inventário do grupo" is on). They render right away with what is in the database, and include the client component `SyncControls` (the "Sincronizar agora" button), next to the "sincronizado há X".
   - If the last sync **started** more than `INVENTORY_STALE_MINUTES` ago (1 since 2026-11-24, like the old app's timer; it was 15), in any status, the component calls the `syncIfStale()` action. Counting the failed ones too avoids hammering BitJita when it is down.
   - While the sync runs, the page shows "Sincronizando com a BitJita…". At the end, the component calls `router.refresh()`.
   - The action checks again, on the server, that the sync really is stale. Two open tabs do not sync twice.
   - The pages export `maxDuration = 60`.
   - The sync does not happen during the page render because, this way, the page opens right away and does not wait for BitJita's 3 to 5 seconds. It also avoids hidden background work.
3. **Daily cron (`trigger = cron`):**
   - `vercel.json` has `{ "crons": [{ "path": "/api/cron/inventory-sync", "schedule": "0 9 * * *" }] }`, that is, at 9h UTC (6h in Brasília). On the Hobby plan, the time is approximate within the hour.
   - The route handler requires `Authorization: Bearer ${CRON_SECRET}`, which Vercel sends by itself.
   - It does nothing if there are no characters or if the sync is up to date (the same rule as today's `scheduled_sync.ts`).
4. **Button (`trigger = manual`):** the `syncNow()` action syncs right away, even if the last sync is recent. The lock still applies.

**Cost on Neon:** each sync wakes the database, which sleeps 5 minutes later. Without a timer, the compute only runs when someone uses the app, plus about 5 minutes per day from the cron.

## Game data import

`scripts/import-game-data.ts`, run from André's PC:

- **Command:** `npm run game-data:import -- [--commit=sha] [--path=pasta]`. The database comes from `DATABASE_URL_UNPOOLED` in `.env`: the direct Neon URL, without the pooler. It also works against local Postgres.
- **Source:** the same as today. It is the BitCraftToolBox/BitCraft_GameData repository, branch `cereal/cs`, folder `static/`, at a fixed commit (the latest, if none is given), or a local folder. `source.ts` and `transform.ts` are ported unchanged: they are pure and already tested.
- **Batch writes,** because the network to Neon makes every round trip to the database expensive. Each table is written with an `INSERT … SELECT * FROM unnest($1::int[], $2::text[], …) ON CONFLICT … DO UPDATE`: one command per table, with all rows in arrays. Today they are batches of 500, plus one round trip per random-list possibility. The children (ingredients, products, possibilities, entries of the techs and of the gathering) of the rows in this import are deleted and inserted again, also with `unnest`.
- **Same rules as today:**
  - runs in a single transaction (with a 5-minute timeout in Prisma's `$transaction`);
  - transforms everything before writing, and a format error writes nothing;
  - running twice gives the same result;
  - what is **new** is counted;
  - what **disappeared** from the source gets `removed_at` (through the different `last_import_id`) and goes back to `null` if it reappears;
  - a `game_id` with a **different name** updates the name and goes into the summary (`renamed`);
  - references to nonexistent items and to unknown skills, tools or stations are skipped and counted;
  - writes a row in `game_data_imports`.
- **New:** `items.item_list_id` is resolved with an `UPDATE … FROM item_lists`. The calculator graph is built and stored in `recipe_graph_snapshots`, and only then is `finished_at` filled in. The app switches graphs by itself when it sees a new import.
- **Output:** the same summary as `bitcraft:import` (counts, new, removed, renamed and ignored references).

## Login

- **Accounts:** `users` with e-mail, name and the password hash, created by `npm run users:create -- --email=… --name=…`. The password is prompted for, hidden, and has at least 12 characters, because the app will be public. There is no signup screen. `LOGIN_REQUIRED` goes away: login is always required.
- **Password:** `scrypt` from `node:crypto`, with a random salt, stored as `scrypt$N$r$p$salt$hash`. The comparison uses `timingSafeEqual`.
- **Session:** a `session` cookie with an HS256 JWT signed with `SESSION_SECRET` (`jose`), carrying `{ sub: userId }`. The cookie is `httpOnly`, `secure` and `sameSite=lax`, and lasts 30 days. "Sair" deletes the cookie.

  - `src/proxy.ts` sends to `/login` every request without a valid session, except `/login`, `/api/cron/*` (which has its own key) and static files.
  - Since the proxy alone is not a security barrier, every action and every route handler calls `requireUser()`.
  - Server actions already check `Origin` against `Host`, which protects against CSRF.
- **Attempts:** after 10 failures for the same e-mail in 15 minutes, login answers "Muitas tentativas. Espere 15 minutos." This uses the `login_attempts` table. The error message does not say whether it was the e-mail or the password.

## Change of 2026-11-24: open signup and separate accounts

André asked, during the deploy, that anyone can create an account through the page, and that each account chooses the characters whose inventory it wants to see. This replaces the "login with two accounts, no signup" and the "group inventory" above.

- **Signup:** `/signup`, open, with name, e-mail and a password of at least 8 characters (also in `users:create`). At most 5 new accounts per IP per day (`users.signup_ip`). The new account is logged in.
- **Plans:** each plan belongs to whoever created it. The owner shares it with another account by e-mail (`plan_shares`): it sees and edits, only the owner deletes and shares. Whoever received it can leave the plan. Another account's plan answers as if it did not exist (404, or "não existe mais" in the actions).
- **Characters:** each account follows up to 5 (`user_game_players`). A character exists once and is read once, even with several accounts following it; with nobody following, it goes away along with its inventory.
- **Inventory:** the stock, the "já tenho" and the "Você tem" are those of the characters of the account that is viewing. In a shared plan, each account uses its own.
- **Sync per character:** `game_players.last_attempt_at` decides who is stale. The page reads only the account's characters not attempted in the last minute; the button reads the account's; the daily cron reads up to 20 characters not attempted in the last hour, the oldest first. Each `sync_runs` stores the account (null in the cron), and the inventory page shows the account's latest one. The lock is still a single, global one.
